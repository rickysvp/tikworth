## 一、PV/UV 埋点修复（根本原因 + 解决方案）

### 1.1 根因分析

当前埋点数据流向：

```
客户端 PageViewTracker   服务端 API 路由
       │                      │
       ▼                      ▼
  /api/track/route.ts    lib/analytics.ts::recordEvent()
       │                      │
   自己建表+自己写入         自己建表+自己写入
  (sha256, 16 chars)       (HMAC-SHA256, 32 chars, 但从不用)
       │                      │
       ├─ ip_hash ✅          ├─ ip_hash ❌ (从未传入)
       └─ user_agent ✅       └─ user_agent ❌ (从未传入)
```

**三个致命问题**：

1. **双写管道分裂**：`/api/track/route.ts` 和 `lib/analytics.ts` 各自独立建表、独立写入，互不知道对方存在。`/api/track` 的 `CREATE TABLE` 里字段可能和 `analytics.ts` 的字段序列不一致。

2. **服务端 recordEvent 没有 IP**：`evaluate/route.ts`、`stripe/webhook/route.ts` 等所有服务端调用 `recordEvent()` 时，**没有传 `ip_hash`、`user_agent`、`referrer`**。这些事件的 `ip_hash` 列全是 NULL。

3. **IP 哈希算法不一致**：`/api/track` 用 `sha256.slice(0,16)`，`lib/analytics.ts::hashIp()` 用 `HMAC-SHA256.slice(0,32)`。虽然目前不影响 UV 计数（因为只用 `IS NOT NULL`），但如果未来需要跨管道关联用户，两套哈希完全对不上。

4. **三处建同一张表**：`lib/analytics.ts`、`/api/track/route.ts`、`/api/stats/route.ts` 各自跑 `CREATE TABLE IF NOT EXISTS analytics_events`。一旦某处改了 schema 而另一处没改，新部署环境和老运行环境会出现字段缺失。

### 1.2 修复方案：统一到 lib/analytics.ts

**原则**：`lib/analytics.ts` 是唯一的埋点真相源。所有写入和查询都通过它。

#### Step 1: 增强 `recordEvent()`，支持从 request 提取元信息

```typescript
// lib/analytics.ts — 新增函数

import { NextRequest } from 'next/server'

/**
 * 从 NextRequest 提取元信息并记录事件。
 * 所有 API 路由统一使用此函数，确保 ip_hash/user_agent/referrer 完整。
 */
export async function recordEventFromRequest(
  req: NextRequest,
  event: Omit<AnalyticsEvent, 'id' | 'created_at' | 'ip_hash' | 'user_agent' | 'referrer'>
): Promise<void> {
  const forwarded = req.headers.get('x-forwarded-for')
  const ip = forwarded ? forwarded.split(',')[0].trim() : '0.0.0.0'
  
  return recordEvent({
    ...event,
    ip_hash: hashIp(ip),
    user_agent: req.headers.get('user-agent') || undefined,
    referrer: req.headers.get('referer') || undefined,
  })
}
```

#### Step 2: 改造 `/api/track/route.ts`，走统一管道

```typescript
// app/api/track/route.ts — 重写
import { NextRequest, NextResponse } from 'next/server'
import { recordEventFromRequest } from '@/lib/analytics'

export async function POST(req: NextRequest) {
  try {
    const body = await req.json()
    // 统一走 lib/analytics，不再自己建表+写入
    await recordEventFromRequest(req, {
      event_type: body.event_type || 'unknown',
      path: body.path || '/',
      username: body.username,
      email: body.email,
      metadata: body.metadata,
    })
    return NextResponse.json({ ok: true })
  } catch (err) {
    console.error('[track] error:', err instanceof Error ? err.message : String(err))
    // 埋点失败不影响主流程，返回 ok
    return NextResponse.json({ ok: true })
  }
}
```

#### Step 3: 改造服务端调用点，传 request

```typescript
// app/api/evaluate/route.ts — 修复示例

// 之前：
recordEvent({
  event_type: 'evaluate_start',
  username: normalized,
  path: '/api/evaluate',
}).catch(err => console.warn(...))

// 之后：
recordEventFromRequest(req, {
  event_type: 'evaluate_start',
  username: normalized,
  path: '/api/evaluate',
}).catch(err => console.warn(...))
```

同样修改：
- `app/api/evaluate/route.ts` — 4 处 recordEvent
- `app/api/credits/claim/route.ts` — 1 处 recordEvent
- `app/api/stripe/webhook/route.ts` — 1 处 recordEvent（webhook 无真实用户 request，保留原 recordEvent 但传空 ip_hash）

#### Step 4: 统一哈希算法，废弃两套并存

```typescript
// lib/analytics.ts — hashIp 保持 HMAC-SHA256，这是主算法
export function hashIp(ip: string): string {
  return crypto.createHmac('sha256', IP_HMAC_KEY).update(ip).digest('hex').slice(0, 32)
}
```

删掉 `/api/track/route.ts` 里自己的 `sha256(ip).slice(0, 16)`。

**迁移影响**：旧数据的 `ip_hash` 是 16 字符 SHA256，新数据是 32 字符 HMAC-SHA256。`COUNT(DISTINCT ip_hash)` 按精确匹配，同一个 IP 在新旧算法下是两个不同的 hash 值 = UV 会被重复计算。

**但这不重要**：UV 本身就是近似指标，HMAC-SHA256 更安全（防彩虹表反查）。从此刻起修正即可，历史数据的 UV 偏差会随时间自然稀释。

#### Step 5: 删除冗余建表

- `/api/track/route.ts` → 删除建表逻辑（改为走 `lib/analytics`）
- `/api/stats/route.ts` → 删除建表逻辑（`lib/analytics` 的 `initDb` 已保证）
- 只保留 `lib/analytics.ts::initDb()` 一处建表

## 二、审计核心问题修复

### 2.1 P0: 中间件鉴权（二选一）

**方案 A（推荐）：删除伪鉴权，在后端路由统一验证**

```typescript
// middleware.ts — 简化版
export async function middleware(request: NextRequest) {
  // Admin API routes: no middleware check needed,
  // each route uses verifyAdminRequest() internally
  return NextResponse.next()
}
```

好处：简单，不重复验证逻辑。每个 admin 路由已经通过 `verifyAdminRequest()` 做了真实 JWT 验证。

**方案 B：中间件做真实验证**

```typescript
// middleware.ts
export async function middleware(request: NextRequest) {
  if (pathname.startsWith('/api/tiktokmaster/')) {
    if (pathname === '/api/tiktokmaster/auth') {
      return NextResponse.next()
    }
    const authHeader = request.headers.get('authorization')
    const token = authHeader?.startsWith('Bearer ') ? authHeader.slice(7) : null
    if (!token) {
      return NextResponse.json({ error: 'Unauthorized' }, { status: 401 })
    }
    const payload = await verifyAdminToken(token)
    if (!payload) {
      return NextResponse.json({ error: 'Unauthorized' }, { status: 401 })
    }
    return NextResponse.next()
  }
  return NextResponse.next()
}
```

**选 A**，因为各路由已经做了认证，中间件再做一次是重复工作，且中间件目前无法访问 verifyAdminToken（需要处理 edge runtime 兼容）。

### 2.2 P0: JWT_SECRET 缺失保护

```typescript
// lib/auth.ts
const JWT_SECRET = (() => {
  const raw = process.env.JWT_SECRET
  if (!raw || raw.length < 32) {
    if (process.env.NODE_ENV === 'development') {
      console.warn('[auth] Using dev JWT secret — sessions will not survive restarts')
      return new TextEncoder().encode('dev-jwt-secret-min-32-bytes-long!')
    }
    throw new Error(
      '[auth] JWT_SECRET is not set or too short (< 32 chars). ' +
      'Set JWT_SECRET environment variable in production.'
    )
  }
  return new TextEncoder().encode(raw)
})()
```

### 2.4 P1: API 限流

```typescript
// lib/rate-limit.ts — 新文件
const ipWindow = new Map<string, { count: number; resetAt: number }>()

export function checkRateLimit(ip: string, limit = 5, windowMs = 60_000): boolean {
  const now = Date.now()
  const entry = ipWindow.get(ip)
  if (!entry || now > entry.resetAt) {
    ipWindow.set(ip, { count: 1, resetAt: now + windowMs })
    return true
  }
  if (entry.count >= limit) return false
  entry.count++
  return true
}
```

在 `evaluate/route.ts` 中：
```typescript
const ip = req.headers.get('x-forwarded-for')?.split(',')[0]?.trim() || 'unknown'
if (!checkRateLimit(ip, 5, 60_000)) {
  return errorResponse('RATE_LIMIT', 'Too many requests', 429)
}
```

### 2.5 P1: 数据库建表收口

将所有建表逻辑统一收口到 `lib/db.ts` 的 `initSchema()` 函数：

```typescript
// lib/db.ts — 新增
export async function initSchema(): Promise<void> {
  const s = await getSql()
  
  // evaluations
  await s`CREATE TABLE IF NOT EXISTS evaluations (...)`
  await s`ALTER TABLE evaluations ADD COLUMN IF NOT EXISTS commerce_readiness JSONB`
  
  // analytics
  await s`CREATE TABLE IF NOT EXISTS analytics_events (...)`
  await s`CREATE INDEX IF NOT EXISTS idx_analytics_type ON analytics_events(event_type)`
  // ... 所有 ALTER TABLE ADD COLUMN IF NOT EXISTS 也在这里
  
  // credit_balances
  await s`CREATE TABLE IF NOT EXISTS credit_balances (...)`
  
  // verification_codes
  await s`CREATE TABLE IF NOT EXISTS verification_codes (...)`
  
  // pending_purchases
  await s`CREATE TABLE IF NOT EXISTS pending_purchases (...)`
  
  // admin_audit_log
  await s`CREATE TABLE IF NOT EXISTS admin_audit_log (...)`
}
```

各模块（auth.ts、credits-server.ts、analytics.ts）改为调用 `initSchema()`，删除各自的建表逻辑。
